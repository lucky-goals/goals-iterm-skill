# Close, clean up, and restore CLI sessions

Use this guide when the user requests Session/Tab/Window closure, idle-session cleanup, or restoration of a closed conversation, or when [automatic cleanup](automatic-cleanup.md) establishes eligibility. See the [standalone runtime contract](runtime.md) for invocation, policy, observations, receipts, and unknown writes. Business completion must be combined with ownership and retention policy; it does not authorize arbitrary terminal closure. Reuse existing authorization and ask only when scope or a specific choice is unresolved.

## Choose the narrowest operation and establish scope

| User intent | Operation |
| --- | --- |
| “Close the session named api-worker” | `close_session` with its exact Session ID; affects that Session only |
| “Close the tab containing this session” | `close_tab` with the bound Session ID; enumerate every pane in the Tab first |
| “Close this window” | `close_window` with the verified Window ID; enumerate all Tabs/Sessions first |
| “Clean up idle sessions” | `clean_all_sessions` only when its entire configured scope is authorized and the request has top-level `authorization_scope: "all_sessions"` |
| “Force-close all sessions, including running tasks” | `clean_all_sessions` with `force=true` only if the entire configured scope and interruption are explicitly authorized, with top-level `authorization_scope: "all_sessions"` |

Pass exactly one selector to `close_session`, `close_tab`, or `close_window`. Nicknames belong to Sessions; each pane may be named separately. Matching uses the complete trimmed, case-folded name; resolve duplicates. Prefer exact IDs for bound tasks. If an original ID disappears, do not substitute a new same-nickname session. Selecting a Tab/Window through a Session affects the whole container, not just that pane.

The runtime selects idle sessions by activity. It does not decide whether a session is useful, task-owned, or idle for long enough. To retain some idle sessions, close other authorized targets individually by exact ID. `clean_all_sessions` has no arbitrary target-list parameter. The fixed installed policy restricts access but does not grant user authorization: `session_ids: null` means the full configured scope; `session_ids: []` means no sessions. If only this task is authorized and policy scope is broader, close exact task Sessions individually; do not invoke global cleanup and expect it to infer ownership. `authorization_scope: "all_sessions"` means all sessions allowed by policy and requires separate user authorization. Force is likewise not task-scoped and never bypasses identity, policy, process, or recovery checks. The runtime protects its own host process and ancestors. Retain and report `SELF_PROTECTION`; never bypass it through another channel.

## Choose the exit path first

For accepted work or explicitly authorized closure of a stopped CLI, prefer [normal exit](natural-exit.md): preserve known recovery details, submit a verified exit command, then verify and normally exit the remaining idle shell. The coordinator does this with the runner's input operations and does not need a separate conversation recovery record before normal exit. This does not change the checks enforced by guarded close operations below. Do not resend a command to an already exited CLI. Existing terminal-cleanup authorization covers eligible shell `exit` without another approval; CLI-exit-only or terminal-retention requests do not expand into cleanup permission.

Use the guarded runtime close path below when interrupting running work, when normal exit is ineligible but the runtime permits safe closure, or when the user explicitly requests force. Force authorization alone does not waive policy, identity checks, receipts, or unknown-outcome protections.

`force=true` does not guarantee immediate closure of an empty Tab. The runtime may first interrupt and verify process exit; an interactive shell may survive interruption. Do not default to force to address a false activity diagnosis on an idle shell. Check normal-exit eligibility first. After `INTERRUPT_UNVERIFIED`, reconcile current state and possible side effects read-only before further shell input; see the normal-exit protocol for conditions.

## Guarded closing path

1. **Discover and locate:** inspect `capabilities --json`, bind original Session/Tab/Window IDs with `list_sessions`, and verify user intent and every container pane. For an explicit, unambiguous single-session request, a dry run may be omitted, but still perform monitor handoff, confirm receipt behavior in the runtime contract, and record intent. For batches, containers, or unclear scope, first invoke the relevant close operation with `dry_run=true` to inspect target and skip results. A dry run is read-only and does not save a close receipt or close anything. A preflight is neither a lock nor a guarantee of later success.
2. **Prevent stale monitoring:** before the first close mutation, persist `closing` for this task's actual targets through a version-checked registry update and new revision. Stop their writing monitors and verify the result. Do not send “continue” or recreate terminals during closure. Keep monitors for preflight-skipped sessions that still need work; do not stop unrelated task monitors. See the [monitoring protocol](monitoring.md).
3. **Save intent and expected observation:** take a fresh `list_sessions.data.observation`, record intent, user authorization, configured policy scope, original targets, force/dry-run choice, and request ID in the audit ledger. Include the observation in the mutation request for existing resources. For `clean_all_sessions`, set top-level `authorization_scope: "all_sessions"` only with explicit authorization covering the full configured scope. A request field cannot widen policy.
4. **Call and verify:** the runtime persists a detailed recovery receipt before interruption/exit/close. Do not interleave exit commands or control keys while a close is running or its outcome is unknown. Normal exit commands remain governed by the separate protocol; Ctrl-C/Ctrl-D are not universal exit commands. Bounded SIGINT/SIGTERM may request CLI exit, but the runtime verifies exit and retains the terminal when unconfirmed. This does not guarantee saved CLI history. Do not interrupt busy/unknown sessions by default. Explicit force authorization permits an interruption attempt, not arbitrary process killing or repeated blind Ctrl-C. Read the complete structured result, including warnings, `side_effects`, and per-session outcomes, then enumerate to verify disappearance. A successful process exit is not terminal closure.
5. **Report actual outcomes:** distinguish closed, skipped, refused, failed, and unknown per Session with reasons and receipt links. Report acceptance, task interruption, CLI exit, terminal closure, and recoverability separately. Do not mark a partially successful batch as all successful. Reconcile unknowns read-only by request ID and fresh topology; never automatically replay a mutation or force-close retry. Do not add new sessions to the original batch without reassessing scope.

Direct `close_session`, `close_tab`, and `close_window` operations should refuse the whole target before mutation when any member is busy/unknown; they must not silently close a subset. `clean_all_sessions` instead selects eligible targets and skips unsafe ones, and it is global only within the configured policy scope. User input or runtime failure after preflight may still produce partial results; report them accurately. A prompt, zero message count, no new output, or one screen read does not establish idleness.

Retain original IDs and actual states for refused/skipped sessions. Resume their monitors only after fresh observation and only if the original work still needs to continue and the user has not asked to stop. Pause writes for unknown outcomes and investigate. Old callbacks must not undo the user's closure intent.

## Recovery receipts and CLI history

Guarded runtime closing persists its recovery receipt before exit; the result reports the record ID and absolute path. Normal exit instead records known recovery details and gaps in the ledger before exiting; that is not a close receipt. The four closing operations are `close_session`, `close_tab`, `close_window`, and `clean_all_sessions`. Read-only `inspect_sessions` reports diagnostics only: it does not register a CLI, save a receipt, restore a conversation, authorize, or close. Readiness fields do not prove ownership or permission. A manually read UUID is not a close parameter. Diagnostics and dry runs may inspect readiness, but neither creates a receipt or grants permission. For each target, check at least:

- Original iTerm Session/Tab/Window IDs, nickname, and CLI type.
- **CLI chat UUID** and its evidence source. This is a CLI conversation identifier, not an iTerm Session ID, PID, or coordination task ID.
- Conversation cwd, usable resume command/arguments, and necessary session-file or record references. Mark unverified fields unknown.
- Whether the runtime recovery receipt was persisted, its ID/absolute path, and whether running work was interrupted. Record actual host observation time; do not claim it is a runtime capture timestamp.

Current adapters recognize Claude Code, Codex, Cursor Agent, and Kiro. Prefer conversation records opened by the process for current identity; Cursor may also use logs opened by that process. A resume UUID in launch arguments proves only the starting conversation, not that it never changed. Even a known UUID cannot authorize interruption when `CLI_IDENTITY_STARTUP_ONLY` is returned. Use records currently opened by the process or current Cursor logs; retain on conflicts. Missing reliable mapping may produce `CLI_IDENTITY_MISSING`. “Latest conversation,” matching cwd, or a session list cannot replace process binding. A skill-recorded UUID is not automatically bound to the live process. Keep the blocker for interruption/guarded closing; assess normal exit independently for missing/startup-only chat identity rather than immediately asking the user to exit manually. Do not send `/status`, `/session-id`, or work to probe identity in a busy or unclear CLI.

Even with an input box, a CLI may be busy/unknown because its shell command remains active. This constrains default guarded closing but does not automatically rule out normal exit. Gather work-completion and interaction evidence under that protocol; do not override state from one screen read or pretend preflight passed. Use existing explicit force permission when actual running work needs interruption.

Distinguish three evidence levels: **current UUID identified → conversation persisted → restoration actually verified**. A UUID or empty new-conversation record does not establish recoverability or tested restoration. Guarded closing skips/refuses a recognized CLI with missing UUID, conflicting identity sources, unknown stable process identity, or failed receipt persistence. Force does not waive these protections. Missing UUID normal-exit eligibility is separate; conflicting sources or unknown processes are not merely degraded recovery. CLI `persistence_status` may be saved/empty/unknown/null and describes conversation history, not receipt persistence. Current behavior does not block solely for empty/unknown history. Act within authorization on actual closing results, report unverified history recovery, and do not invent `RECOVERY_PERSISTENCE_FAILED`. An ordinary shell/job may return empty `cli_sessions`, meaning no chat records were returned this time, not that the terminal never hosted a CLI. Preserve historical conversation references in the task ledger. Treat misidentification or missing evidence as blockers; an empty array is not proof of safe recovery.

Receipts hold recovery data; ledgers hold actions, evidence, and outcomes. Reference exact `recovery_record_id` and `recovery_record_path` fields. New receipts live under `~/.local/state/goals-iterm-skill/recovery`; use the actual returned path. Do not replace a failed initial receipt with a host-created file and retry closure. A receipt's pre-operation snapshot may still show interruption/exit/closure as pending; it is not the final result. Reconcile returned result arrays, receipt steps, and current topology. A receipt's existence does not prove later log entries are complete. An update failure may follow interruption/closure; inspect unknown/partial and per-item results instead of claiming no side effects. With a lost response, query the known request ID and inspect current topology. If the exact record mapping is unknown, retain uncertainty rather than choosing the newest file. Never put credentials in records or user reports.

## Restore a closed conversation

1. Locate the correct CLI conversation from the original target and recovery record. Check UUID, cwd, persistence evidence, and unfinished actions. If only a UUID exists without conversation storage, report unverified recovery rather than promising resumption.
2. Restore into an available dedicated session as requested. Verify shell state and cwd first. Construct the command from `resume.executable` and each `resume.argv` element with correct quoting, using cwd. For missing arguments or unclear versions, read local help in a ready dedicated shell. Do not directly concatenate arguments containing spaces/special characters or send natural-language continuation instructions to a shell.
3. Verify the loaded conversation's identity and contents, recording the new iTerm Session ID's relationship to the original CLI chat UUID. Do not dispatch work if identity cannot be confirmed or silently fall back to a new conversation that repeats the work.
4. If continuing the original task, check prior external side effects and artifacts first, then resume unfinished work. Update generation, single-writer ownership, ledger, and monitor. For interface-only restoration, stop once ready without adding work.

## Focused validation scenarios

| Scenario | Expected action |
| --- | --- |
| Two differently named panes; user wants only one closed | Exact `close_session`, retaining the other pane in the Tab |
| Two Session nicknames differ only by case | Reject ambiguous nickname selection and bind an exact ID |
| One idle and one busy pane; ordinary whole-Tab close | Refuse the whole target; do not close the idle pane first |
| Global cleanup includes idle, busy, and unknown sessions | Confirm full configured scope authorization and top-level scope field, then report per-item blockers |
| Only this task's cleanup is authorized, policy spans several projects | Close original task IDs individually; do not use `clean_all_sessions` |
| Force authorized but chat UUID missing or recovery receipt write fails | Report the blocker; do not bypass protections |
| Force authorized, reliable UUID and writable receipt, history unknown/empty | Use actual close results and report unverified recovery, not fabricated receipt failure |
| Dry-run result contains blockers | Explain each result; do not assume a receipt was persisted or every target is eligible |
| User starts work or adds a pane after preflight | Refresh observation and targets; preflight is not a lock or scope expansion |
| Close response is lost and a late callback arrives | Keep closing/unknown; reconcile by request ID without replay or recreation |
| Startup-only UUID with `CLI_IDENTITY_STARTUP_ONLY` | Guarded interruption/closure remains blocked; independently eligible normal exit may proceed with recovery unverified |
| Current UUID visible but conversation not persisted | Record identified identity and unverified recovery; do not promise restoration |
| Resume command opens a new conversation | Do not dispatch; report identity mismatch and inspect the recovery record |

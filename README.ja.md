# goals-iterm-skill

Skill バージョン: [v0.2.2](https://github.com/lucky-goals/goals-iterm-skill/releases/tag/v0.2.2)

[プロジェクトサイト](https://lucky-goals.github.io/goals-iterm-skill/)
[English](README.md) | [简体中文](README.zh-CN.md) | [繁體中文](README.zh-TW.md) | [日本語](README.ja.md)

coding agent から [goals-iterm-mcp](https://github.com/lucky-goals/goals-iterm-mcp) を通じて、iTerm2 上の Claude Code、Codex などの CLI に作業を指示する skill です。進捗の監視、判断の支援、完了条件の確認まで継続して行います。

インライン監視では、待機に入るたびに短い進捗報告を行います。最新の観測に基づく現在の作業、今回待っている結果、次回の確認間隔、残りの作業を伝えます。段階の変化や問題は速やかに報告し、新しい出力がなければその旨を明示します。根拠のない進捗率や完了時刻は示しません。報告はユーザー向けであり、操作対象の CLI には送信しません。バックグラウンド監視は変化がない限り通知を控えます。[進捗報告の手順](references/monitoring.md#内联等待的进度旁白)を参照してください。

## 必須の MCP：goals-iterm-mcp

この skill は **[lucky-goals/goals-iterm-mcp](https://github.com/lucky-goals/goals-iterm-mcp)** を使って iTerm2 を操作します。まず**調整役の agent のクライアント**に MCP を導入して接続し、次にこの skill をインストールして、以下のタスク用プロンプトを使用してください。skill だけでは端末操作ツールは提供されません。MCP が接続済みなら、重複して導入せず接続を確認してください。

準備の順序：

1. 端末を実行する Mac に iTerm2 をインストールして起動し、**Settings → General → Magic → Python API** を有効にします。認可ダイアログが表示されたら接続を許可します。
2. 調整役のクライアントに goals-iterm-mcp をローカル stdio サーバーとして設定します。クライアントはその Mac にアクセスできる必要があります。クラウドだけで動くチャットからローカル iTerm2 を直接操作することはできません。
3. iTerm2 に Claude Code、Codex などの対象 CLI をインストールし、認証を済ませます。新しいタブでも正常に起動することを確認し、認証情報をプロンプトに含めないでください。
4. MCP のツール検出と読み取り専用の `list_sessions` 呼び出しを確認してから、この skill をインストールします。作業の実行には入力用ツールが必要です。`--read-only` サーバーでは監視のみ可能です。

詳しい手順とバージョン更新は [MCP インストールガイド](https://github.com/lucky-goals/goals-iterm-mcp/blob/main/README.ja.md)を参照してください。以下はガイドに記載された `0.1.2` を固定して使う例であり、将来のバージョンが非互換という意味ではありません。

```text
この Mac 上で [対象クライアント] に goals-iterm-mcp を導入してください。
リポジトリ：https://github.com/lucky-goals/goals-iterm-mcp

1. プロジェクトのインストールガイドを読み、macOS、iTerm2、uv/uvx を確認してください。
   uv がなければ、uv の公式手順に従ってインストールしてください。
2. Python 3.12 でパッケージの起動を確認してください：
   uvx --python 3.12 goals-iterm-mcp@0.1.2 --help
3. クライアントの既存 MCP 設定をバックアップし、iterm という名前のローカル stdio
   サーバーを追加または更新してください。無関係な設定は保持し、重複を避けてください：
   command：この Mac の uvx の絶対パス
   args：["--python", "3.12", "goals-iterm-mcp@0.1.2", "serve"]
   対象クライアントが対応する設定形式と配置先を使用してください。
4. 必要に応じて iTerm2 Python API の有効化と認可ダイアログの操作を案内してください。
   対応する方法で MCP を再読み込みし、手動で再起動が必要なら手順を示してください。
5. ハンドシェイク、ツール検出、list_sessions のみで接続を検証してください。
   導入中は端末内容の読み取り、入力送信、ウィンドウの作成や終了、coding タスクの開始を
   行わないでください。
6. 設定の配置先、固定したバージョン、接続結果を報告してください。単体のサーバー接続と、
   対象クライアントでのツール読み込みを区別し、問題があれば残りの手順を示してください。
   準備ができたら、続く説明に従って skill をインストールしてください。
```

`serve` はクライアントが stdio 経由で起動する MCP サーバーの入口であり、coding CLI ではありません。MCP の導入では monitor の提供や対象 CLI の認証設定は行われません。

## インストール済みの旧版を更新

ユーザーが tag または commit を指定しない限り、`goals-iterm-skill` の最新版はリモートリポジトリのデフォルトブランチにある最新の公開コミットです。ローカルのソースだけを更新しても、コピーされたインストール先は更新されません。この skill は PyPI パッケージではなく、`goals-iterm-mcp` の PyPI パッケージを更新しても skill は更新されません。

下のプロンプトをローカルファイルにアクセスできる coding agent に渡し、`[対象クライアント]` を置き換えてください。

```text
[対象クライアント] が実際に読み込んでいる goals-iterm-skill を更新してください。
リポジトリ：https://github.com/lucky-goals/goals-iterm-skill
（固定版を使う場合は、ここに tag または commit を指定してください。）

1. 対象クライアントが実際に読み込んでいるインストール先と適用範囲を確認し、Git checkout、symlink、コピーしたディレクトリ、クライアント管理のインストールのどれかを特定してください。パスを推測しないでください。現在の ref/commit またはファイル状態とローカル変更を報告し、重複インストールも確認してください。確認できなければ unknown と明記し、別のコピーを追加しないでください。
2. 読み込まれているインストール全体とローカル変更を、発見した skill ディレクトリの外にある明確な場所へバックアップしてください。symlink の場合はリンクだけでなく実際のリンク先の内容をバックアップしてください。バックアップが二つ目の skill として検出されないようにし、監査/実行時状態と他の skill を保持してください。
3. リモートから取得し、リモートリポジトリのデフォルトブランチにある最新コミットを解決してください。私が tag または commit を指定した場合だけそれを使い、デフォルトブランチが main だと決めつけないでください。対象 SHA を記録し、古い checkout や未コミット変更を upstream の最新版と説明しないでください。
4. きれいな状態で意図したブランチを追跡している checkout だけは fast-forward で更新してください。dirty、分岐、detached、別ブランチの場合は reset、変更の破棄、強制切り替えを行わず、新しい upstream checkout と比較してローカル変更を保持・統合してください。統合できない競合は明確に報告してください。
5. symlink なら実際のリンク先を更新してください。コピーしたインストールなら新しい完全な checkout と比較し、SKILL.md、references/、agents/、scripts/ を含む package 全体を同期してください。SKILL.md だけをコピーしないでください。バックアップ後に削除するのは package 所有で古いと確認できたファイルだけにし、不明な追加ファイルは残してください。クライアント管理のインストールは対応する更新機能を使ってください。
6. skill の metadata、相対リンク、インストール内容が対象コミットに対応することを検証し、クライアントが対応する方法で再読み込みしてください。手動操作が必要なら正確な手順または新しい session が必要なことを示してください。クライアントが新しい revision とファイルを実際に認識したことを確認し、現在開いている chat が hot-reload されるとは説明しないでください。
7. MCP の接続とツール検出は別に確認してください。接続確認を行う場合も、読み取り専用の list_sessions だけを使ってください。更新中は端末内容の読み取り、入力送信、ウィンドウの作成や終了、タスクの開始を行わないでください。新しいツールがなければ、MCP の別途アップグレードまたは再読み込みが必要だと報告し、MCP の固定や無関係な設定を自動変更しないでください。
8. インストール先と適用範囲、方式、バックアップ先、更新前後の ref/commit SHA、ローカル変更、検証と再読み込みの結果、ローカル変更を保持した rollback 方法を報告してください。
```

手動 fallback：意図したブランチを追跡するきれいな checkout では、対象 ref を確認してから `git fetch <remote>` と `git pull --ff-only` を実行してください。それ以外の状態では新しい checkout と比較します。コピーしたインストールは一時ディレクトリで対象コミットを取得し、新しい checkout と比較、バックアップ後に package 全体を同期し、古い package ファイルを確認してからクライアントの方法で再読み込みします。symlink は実際のリンク先を更新します。rollback では更新後に追加されたローカル変更を保持してバックアップを復元してから再読み込みし、skill の rollback で MCP や既に実行した端末タスクを戻せないことも報告してください。

## 前提条件と手動インストール

リポジトリのルートが skill パッケージです。宿主クライアントの対応する方法で、ディレクトリ全体を `goals-iterm-skill` としてインストールしてください。相対参照を維持するため、`SKILL.md`、`references/`、`agents/`、`scripts/` を一緒に配置します。`scripts/` にはローカルセッションレジストリで使う標準ライブラリの補助スクリプトが含まれます。配置先と再読み込み方法は、対象クライアントのドキュメントおよび既存設定に従ってください。

この skill は MCP のインストールや独立したバックグラウンドサービスを提供しません。宿主で goals-iterm-mcp に接続し、iTerm2 Python API を有効にして、対象端末で CLI と認証を準備してください。セッション一覧、画面/履歴の読み取り、テキスト/キー送信のツールが必要です。新しい端末の作成には対応する作成ツールも必要です。

継続監視には、宿主のスケジューリング/再開機能、または agent の実行中に行うポーリングが必要です。バックグラウンドで agent を再開できないクライアントでは、agent の実行終了後に自動監視を継続できません。この制約を明確に報告するよう skill が指示します。

### セッションのライフサイクルと永続的な調整状態

新しい CLI 作業を開始または引き継ぐ前に、[セッション・ライフサイクルガイド](references/session-lifecycle.md)に従ってください。新しい CLI プロセスまたはセッションを起動する前に、インストール済み MCP が実際に提供するクリーンアップと復旧の機能を確認します。CLI の起動後、作業を送る前に、会話の永続化状態と現在の Session/Tab/Window の識別情報を確認してください。transcript または履歴が無効になっている場合は、その CLI が対応し、検証済みの起動方法で修正してから新しい作業を送ります。設定を変更するためだけに、すでに動作中のセッションを再起動してはいけません。CLI の識別情報や復旧レシートだけでは、履歴が永続化され再開できる証拠になりません。復旧状態が不明な場合は、明示的で実行可能な手動フォローアップとして記録し、自動クローズを約束しないでください。

調整役は `~/.local/state/goals-iterm-skill/session-registry.json` に永続的なローカルレジストリを保持します。パッケージに含まれる標準ライブラリだけの補助スクリプト `scripts/session_registry.py` を使い、lock、revision、generation のガードを適用してください。レジストリの記録はホスト側の観測であり、MCP の権威でも、実際の端末に対するロックでもありません。タスクをまたぐ handoff/再利用だけが古い完了状態を無効にします。同じタスク内で調整役だけを引き継ぐ場合は、記録済みの業務・クリーンアップの事実（unknown の結果を含む）を保持し、generation ガードによって古い書き込みだけを防ぎます。CLI のチャット名を変更しても、新しい識別情報にはなりません。セッション単位のタスクが受け入れられたら `finalizing` に移し、業務上の書き込みを行う monitor は停止します。ただしクリーンアップの調整は継続し、所有する各リソースが実際に `closed`、明示的な `retained`、または実行可能な処置を伴う `blocked` になるまで続けてください。unknown のクリーンアップ結果は可視のまま保持し、変更する前に読み取り専用で照合します。消費者が不要になった子タスクは、独立して受け入れまたは回収できます。

クリーンアップの再確認は範囲を限定し、実際のスケジューラと認可がある場合だけ再試行します。書き込み結果が不明なときは、読み取り専用の観測でのみ照合してください。既定で `force` やグローバルな一括処理を行ってはいけません。最終報告には、リソース集計の合計と理由、復旧の証拠、残っているフォローアップを含めます。

## 明示的なセッションのクリーンアップ

現在の MCP ソースは 4 つのクリーンアップツールを実装しています。インストール済みサーバーが対応する schema を公開している場合だけ使用してください。実行時はインストール済みツールの schema が優先されます。この節は現在の実装を説明するもので、パッケージのリリースやバージョン変更を示すものではありません。

- `close_session(session_id OR nickname, force=false, dry_run=false)` は 1 つのセッションを閉じます。
- `close_tab(tab_id OR session_id OR nickname, force=false, dry_run=false)` は 1 つのタブを閉じます。
- `close_window(window_id OR session_id OR nickname, force=false, dry_run=false)` は 1 つのウィンドウを閉じます。
- `clean_all_sessions(force=false, dry_run=false)` はサーバーが許可する範囲のセッションをクリーンアップします。

最初の 3 つのツールには 1 つだけセレクターを指定します。ID は完全一致で扱います。ニックネームは前後の空白を取り除き、大文字小文字を折りたたんだ上で、1 つの Session に完全一致させます。タブ/ウィンドウのツールでは、その Session を含むコンテナを選び、ニックネームを Tab として直接扱いません。複数候補に一致する場合は拒否します。既定では `clean_all_sessions` はアイドル状態だと確認できたセッションだけを閉じ、実行中、待機中、不明、または安全性を確認できないセッションはスキップします。「不要」や有用性を推測せず、調整役の agent は要求された保持方針と認可範囲を守る必要があります。`force=true` では初期の認可範囲にあるすべてのセッション（実行中を含む）を試みますが、ID、権限、対象変更、復旧の安全確認は省略しません。通常の close は、影響を受けるセッション/タブ/ウィンドウの事前確認で実行中または不明なセッションが見つかると、force が認可されていない限り全体を拒否します。

中断、CLI の終了、またはネイティブなクローズの前に、サービスは必ず対象と、取得できた CLI/chat UUID、cwd、再開メタデータを含むプライベートな復旧レシートを永続化します。最初のレシート保存に失敗した場合は、端末への書き込み前に停止します。後続のレシート更新は操作後に失敗する場合があるため、各セッションの結果を確認してください。その後 CLI の正常終了を依頼し、終了を確認してから対象を閉じます。`dry_run=true` は完全な読み取り専用です。端末入力、復旧レシートの保存、名前変更、中断、クローズは行いません。

各セッション結果は公開フィールド `interruption`、`exit`、`closure_status`、`cli_sessions` を使用します。チャット記録には `cli`、`chat_uuid`、`cwd`、識別情報の取得元、永続化状態、再開データが含まれる場合があります。レシートがある場合、操作は `recovery_record_id` と `recovery_record_path` を返します。CLI 履歴の `persistence_status` が空または不明でも、それだけで阻害要因にはなりません。UUID の識別情報と復旧レシートの安全保護は、履歴が実際に永続化され再開できるかどうかとは別です。ID だけで再開を保証しません。MCP の応答が `isError=true` でも、`status` と `closed_sessions`、`skipped_sessions`、`failed_sessions`、`unknown_sessions` の配列を読み取ってください。

### タスク所有リソースの自動回収

受け入れ条件を確認して監視を停止した後、既定ではタスク専用に作成したリソースを自動回収します。終了ツールは内部で復旧レシートを永続化してから、CLI を終了するか端末を閉じます。CLI が「done」と主張しただけでは受け入れの証拠になりません。既存の借用セッションとウィンドウは、タスク用に明示的に採用し、クリーンアップ認可を得ない限り保持します。ユーザーが開いたままにする指定をしたリソースも保持します。

リソースの作成時または明示的な採用時に、起点、所有タスク、正確な Session、Tab、Window ID を記録します。最大で安全な、重複しない所有コンテナを選びます。現在のすべての子孫がこのタスクに属し、完了して回収対象である場合だけタスク専用 Window を使い、それ以外はタスク専用 Tab、さらにそれ以外は所有され回収対象である個々の Session を使います。空であることや専用に見えることだけでは所有を証明できません。クリーンアップ認可のない借用した親、および共有または不明なペインは保持します。allowlist が不完全でコンテナの所有を証明できない場合は、正確な Session 単位を使います。

自動回収では `dry_run=true` でプレビューし、構成を再確認してから、`force=false` で `close_window`、`close_tab`、または `close_session` を呼び出します。グローバルな `clean_all_sessions` は呼び出しません。事前確認で busy、unknown、識別情報の欠落、または初期復旧レシートのエラーが報告された場合は、リソースを保持して報告します。実行開始後のエラーには副作用があり得るため、端末が保持されたと断定せず、実際の結果を確認します。自動で force にしたり、盲目的に再試行したりしません。force の明示的なユーザー認可は、既存の手動フローとして別に扱います。

業務上の完了とクリーンアップ結果を分けて扱います。監査記録には各セッションの CLI/chat UUID、cwd、再開メタデータ、復旧レシート、クリーンアップ結果を書き込みます。paused、failed、canceled のタスクは自動回収しません。既存の監視・監査ワークフローはそのまま適用され、実際にインストールされたツールの schema が実行時の基準です。借用リソース、グローバルなクリーンアップ、force によるクリーンアップには引き続き明示的な認可が必要です。既存の認可を再利用し、繰り返し承認を求めません。`clean_all_sessions` は無関係なタスクにも影響し得るため、許可された範囲がサーバーの範囲（設定された allowlist を含む）と一致する場合だけ呼び出してください。詳細な手順は[自動回収・復旧ガイド](references/automatic-cleanup.md)と[終了・復旧ガイド](references/closing-and-recovery.md)を参照してください。

## 使用例

```text
goals-iterm-skill を使い、iTerm 上の Claude Code に /path/to/project の
ログイン問題を修正させてください。まず原因を調査し、修正後は関連テストだけを実行して
ください。指示するたびに応答を監視し、通常の技術判断はあなたが行ってください。
ネットワークエラーでタスクが停止し、自動再開しないと確認できた場合は復旧してください。
完了条件を満たしたら業務上の書き込みを行う monitor を停止し、所有するリソースが閉じられた、
明示的に保持された、または実行可能な処置を伴ってブロックされた状態になるまで、認可された
終了処理を完了してください。変更、テスト、リソース集計の合計と理由、復旧の証拠、残っている
フォローアップをまとめてください。
公開・リリースは行わないでください。
```

既存セッションのニックネームを指定してタスクを引き継ぐこともできます。skill は正確な `session_id` を確認し、実行中の作業を重複して送信しません。

## 応用例：Goal を使ってタスク全体を完了まで進める

複数の段階があるタスクでは、宿主が対応している場合、調整役の Codex チャットに Goal を設定することを推奨します。iTerm 内で作業を実行する CLI に別の Goal を設定する必要はありません。Goal は全体の目標を保持し、skill は調整手順を指示し、monitor は端末の応答を監視します。Goal は monitor の代わりにはならず、独立したバックグラウンドサービスを提供するものでもありません。[公式 Goals ガイド](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)を参照してください。

以下の項目を置き換えて、調整役の Codex に渡してください。宿主が Goal に対応していない場合は、Goal の作成と完了の指示を省き、監視と完了条件の確認に関する指示を残してください。

```text
Codex Goal を作成して開始してください。$goals-iterm-skill を使い、
iTerm MCP 経由で端末内の Coding CLI に継続して指示し、以下のタスクが
完了条件を満たすまで進めてください。

プロジェクトディレクトリ：[絶対パス]
実行する CLI：[Claude Code / Codex CLI]
対象セッション：[既存のニックネームまたは ID。なければ専用セッションを作成]

タスクの目標：
[最終的に実現したい結果]

完了条件：
1. [確認可能な機能や動作]
2. [成功する必要がある関連テスト]
3. [納品するファイル、結果、または説明]

実行要件：
- 実行と並行して Markdown 監査台帳を維持してください。指示、CLI の応答と判断待ち事項、
  判断とその根拠、実際の操作と結果を、時刻、外側/CLI ラウンド、関連イベント番号とともに
  記録してください。開始時に保存先を示し、最終報告に台帳のリンクを付けてください。
- あなたは調整、監視、判断、結果の確認を担当し、具体的な開発作業は対象 CLI に任せてください。
- 最初にセッションの状態を確認してください。タスクが既に実行中なら、重複して指示せず
  監視を引き継いでください。
- タスク、追加指示、判断、復旧指示を送るたびに、同じ monitor を作成または更新してください。
- 宿主で実際に使える監視機構を利用してください。バックグラウンドで再開できない場合は、
  実行中にポーリングを続け、その制約を正確に説明してください。「後で確認する」という
  約束だけで済ませないでください。
- 通常の技術判断は文脈とプロジェクトの規約に基づいて自ら行い、advisor として CLI の
  作業継続を支援してください。
- CLI が作業中または自動再試行中なら監視を続け、タスクを再送しないでください。
- タスクが停止し、自動再開しないことを確認した場合に限り、完了済みの作業を確認したうえで
  回数を制限して復旧してください。
- 途中経過の報告、待機中の入力欄、CLI の完了宣言だけでタスク全体が完了したと判断しないでください。
- 完了条件の証拠が不足していれば追加確認を求めてください。すべての条件を満たしたら、業務上の
  書き込みを行う monitor を停止し、認可された終了処理だけを完了してください。各リソースを
  閉じられた、明示的に保持された、実行可能な処置を伴ってブロックされた、または unknown として
  記録します。unknown は読み取り専用で照合し、隠さないでください。必須の作業が残っていない
  場合だけ Goal を完了にします。必須の作業やクリーンアップが本当に阻害されている場合は、宿主の
  現在の状態と必要な操作を正確に報告し、その状態遷移の規則に従ってください。blocked への即時の
  遷移を強制したり、Goal を無期限に開いたままにすると約束したりしないでください。変更、検証結果、
  リソース集計の合計と理由、復旧の証拠、残っているフォローアップをまとめてください。消費者が
  不要になった子タスクは独立して受け入れまたは回収できます。

制約：
- プロジェクトの AGENTS.md に従ってください。
- 関連するテストに絞り、必要がなければ全テストを実行しないでください。
- Python プロセスの起動時に --reload を使用しないでください。
- このタスクでは公開、プッシュ、破壊的操作を許可しません。
- 私の判断が必要な場合は、具体的な質問、推奨案、必要な操作を提示してください。
  文脈を保存し、関連する自動入力を停止してください。
```

## タスクの監査台帳

委託タスクごとに、実行と並行して Markdown の監査台帳を維持します。調整役は指示、CLI の応答（判断待ちの質問と選択肢を含む）、判断とその根拠、送信の証拠、復旧、完了条件の確認、監視の終了処理を記録します。各記録には UTC オフセット付きの時刻、外側の会話ラウンド、セッションごとの CLI ラウンド、関連イベント/判断 ID を付けます。外側のラウンドはタスク内のユーザーメッセージ番号であり、宿主の実際のチャット ID とは区別します。

開始時に台帳の絶対パスを示し、最終報告にリンクを付けます。保存先は指定可能です。指定がなければ宿主の非公開状態ディレクトリを使い、それがなければ `~/.local/state/goals-iterm-skill/audits/` を使います。台帳をプロジェクトに自動コミットすることはありません。機密情報を伏せ、変化のないポーリングは集約できますが、重要な応答と判断は残します。これは追記を基本とする操作記録であり、改ざん防止ログや端末の完全な録画ではありません。

[監査プロトコル](references/audit.md)と [Markdown テンプレート](references/audit-template.md)を参照してください（現在は簡体字中国語）。送信前に予定を記録し、送信後に実際の結果を追記します。記録できない場合は欠落を報告して新たな自動作業指示を止め、記録なしで黙って継続しません。

## 保守と検証

入口は [SKILL.md](SKILL.md) です。ツールの仕様は [iterm-tools.md](references/iterm-tools.md)、監視、復旧、動作検証シナリオは [monitoring.md](references/monitoring.md)、クリーンアップの復旧詳細は [closing-and-recovery.md](references/closing-and-recovery.md) を参照してください。これらの指示ファイルは現在、簡体字中国語で記述されています。ツールの取り決めは cc-iterm-mcp の `src/goals_iterm_mcp/direct.py` に基づいていますが、実行時はインストール済みツールの schema を優先します。

変更後は skill の frontmatter と相対リンクを検証し、監視プロトコル末尾のシナリオを確認してください。実際の CLI 検証には専用のテストセッションを使い、指示の送信、判断、復旧、監視の終了処理を確認します。静的検証だけでは、バックグラウンドのスケジューリングや実際の CLI 連携が動作することは保証されません。
